# План реализации: k-NN топология + временная динамика сети

## 0. Контекст

Сейчас `vostok` решает **статическую однократную задачу**: один раз генерируются истинные координаты, один раз — зашумлённые («мнимые») координаты и полная матрица попарных расстояний `n×n`, после чего градиентный спуск и EKF по одному разу «дорешивают» эту единственную сцену. Обмен измерениями идёт **между всеми парами узлов** (полносвязный граф, `C(n,2)` измерений).

Требуется добавить две функции:

1. **Разреженная топология обмена** — узел обменивается измерениями только с k ближайшими соседями, а не со всей сетью.
2. **Временная динамика** — координаты объектов меняются со временем, а точность знаний узла о собственном положении деградирует по заданному математическому закону; нужно измерить, насколько хорошо связка ГД+EKF компенсирует это нарастание ошибки.

Обе функции меняют систему не аддитивно, а **концептуально**: из «решателя одной сцены» `vostok` превращается в **симулятор трекинга во времени по разреженному графу связи**. Ниже план разбит на глобальную архитектуру, детальные изменения по файлам и поэтапный roadmap.

## 1. Глобальное концептуальное изменение архитектуры

### 1.1 Было

```
generate scene (once) → RunGradientDescent (once, full mesh) → RunEKF (once, full mesh) → analyze (once)
```

Матрица расстояний `distances[n][n]` — единственный источник измерений, статична с момента генерации до конца программы. `realCoords []Point` — отдельный параллельный слайс, живущий только в `main.go`.

### 1.2 Стало

```
generate scene (once)
  → build kNN graph (topology)
  → for tick := 0..ticks:
        StepTrueMotion        (истинное положение узлов дрейфует)
        GrowUncertainty        (точность "знания" узла о себе падает по мат. закону)
        RecomputeDistances     (новые зашумлённые измерения по новым истинным координатам)
        RebuildKNNGraph        (топология связи могла измениться — узлы переместились)
        RunGradientDescent     (warm start от предыдущего тика, только по соседям k-NN)
        RunEKF                 (warm start, только по рёбрам k-NN графа)
        CollectTickMetrics     (сырая ошибка vs скомпенсированная ошибка)
  → AnalyzeTickHistory (оценка тренда компенсации во времени)
```

Ключевые концептуальные сдвиги:

- **Граф обмена данными перестаёт быть подразумеваемым (implicit full mesh)** и становится явной структурой данных (`NeighborGraph`/`[]Edge`), которая пересчитывается на каждом тике и передаётся в `RunGradientDescent`/`RunEKF` как параметр.
- **`Node` перестаёт быть статическим снимком** и приобретает временное состояние: истинное положение (`TrueCoord`), «то, что узел о себе думает» (`BelievedCoord`) с растущей неопределённостью (`Uncertainty`), и то, что реально стало «эксплуатационным» результатом (`CurrentCoord`).
- **EKF/GD переходят из режима "batch-решение одной сцены" в режим "рекуррентный трекер"**: между тиками состояние не пересоздаётся с нуля, а продолжается (warm start), что соответствует реальному online-использованию фильтра Калмана.
- **`realCoords []Point`, гулявший параллельным слайсом по `main.go`, поглощается в `Node.TrueCoord`** — иначе при движении пришлось бы синхронизировать два параллельных источника истины, что является частым источником багов.
- **Генерация дистанций (`distances`) становится переиспользуемой операцией**, а не одноразовым блоком кода в `main.go` — она вызывается на каждом тике.

## 2. Часть A — обмен данными только с k-ближайшими объектами

### 2.1 Новые функции/типы в `utils.go`

```go
// NeighborGraph — граф соседства: graph[i] — индексы узлов, с которыми узел i
// обменивается измерениями расстояний.
type NeighborGraph [][]int

// Edge — единичное ребро обмена данными между узлами (I < J, без дублей).
type Edge struct {
    I, J int
}

// BuildKNNGraph строит граф k-ближайших соседей ПО ИЗМЕРЕННЫМ (зашумлённым)
// расстояниям — узел физически не может знать реальные расстояния лучше,
// чем их измеряет его собственный дальномер.
//
// mode:
//   "mutual" — ребро (i,j) существует, только если КАЖДЫЙ считает другого
//              одним из k ближайших (реалистичная модель радиосвязи "слышит оба").
//   "union"  — ребро существует, если ХОТЯ БЫ ОДИН считает другого k-ближайшим.
func BuildKNNGraph(distances [][]float64, k int, mode string) NeighborGraph

// EdgesFromGraph дедуплицирует NeighborGraph в плоский список рёбер (i<j).
// Именно этот список задаёт вектор измерений для EKF и является единой
// "картой связей" для всей итерации.
func EdgesFromGraph(g NeighborGraph) []Edge

// CheckConnectivity для каждого подвижного (не-анкерного) узла проверяет,
// существует ли путь по графу соседства хотя бы до одного анкера (BFS/DFS).
// Возвращает индексы узлов, которые оказались "оторваны" от анкеров —
// для них геометрия нерешаема (GD/EKF будут держать их только на
// регуляризационном якоре BelievedCoord).
func CheckConnectivity(g NeighborGraph, nodes []*Node) []int

// EnsureMinDegree — защитный пост-проход: если у узла 0 соседей (например,
// в mode="mutual" на границе площадки), принудительно добавляет ребро до
// его ближайшего по измерению узла, чтобы не потерять узел из графа целиком.
func EnsureMinDegree(g NeighborGraph, distances [][]float64) NeighborGraph
```

### 2.2 Изменения в существующих функциях

**`gradient.go` — `RunGradientDescent`**

```go
// Было:
func RunGradientDescent(nodes []*Node, distances [][]float64, alpha, lambda, epsilon float64, maxIter int)

// Стало:
func RunGradientDescent(nodes []*Node, distances [][]float64, graph NeighborGraph, alpha, lambda, epsilon float64, maxIter int)
```

Внутренний цикл `for j := 0; j < n; j++ { if i == j { continue } ... }` заменяется на `for _, j := range graph[i] { ... }`. Логика самого градиента (errRatio, регуляризация к `InitialCoord`) не меняется — меняется только множество `j`, по которому он суммируется.

**`ekf.go` — `RunEKF`**

```go
// Было:
func RunEKF(nodes []*Node, distances [][]float64, iterations int, q, r float64)

// Стало:
func RunEKF(nodes []*Node, distances [][]float64, edges []Edge, iterations int, q, r float64)
```

- `numMeas` больше не считается как `C(n,2)`, а берётся как `len(edges)`.
- Двойной цикл `for i := 0..n { for j := i+1..n { ... } }`, строящий `H`/`Z`/`Zcalc`, заменяется на одиночный `for measIdx, e := range edges { i, j := e.I, e.J ... }`.
- Остальная математика (Якобиан, инновация, обновление `P`, `K`) не меняется — она уже была рассчитана на произвольный размер вектора измерений.

**`main.go`**

- После генерации `distances` строится граф: `graph := BuildKNNGraph(distances, k, neighborMode)`, затем `graph = EnsureMinDegree(graph, distances)`, `edges := EdgesFromGraph(graph)`.
- Перед запуском алгоритмов — вывод диагностики: `disconnected := CheckConnectivity(graph, nodes)`, предупреждение в консоль, если список не пуст.
- Вызовы `RunGradientDescent(...)`/`RunEKF(...)` дополняются параметрами `graph`/`edges`.

### 2.3 Конфигурация

Новая секция в TOML (`utils.go: Config`):

```go
Topology struct {
    K            int    `toml:"k"`
    NeighborMode string `toml:"neighbor_mode"` // "mutual" | "union"
} `toml:"topology"`
```

Новые CLI-флаги в `main.go`, зеркальные существующему паттерну: `-k` (по умолчанию `n-1`, что даёт полносвязный граф = текущее поведение), `-neighbor-mode` (по умолчанию `"mutual"`).

**Важно для валидации**: при `k >= n-1` граф обязан выродиться ровно в текущий полносвязный вариант — это и есть regression-тест перехода (см. §5, Фаза B).

### 2.4 Риски

| Риск | Митигация |
|---|---|
| При малом k и `mode="mutual"` граф теряет связность, часть подвижных узлов не имеет пути до анкера | `CheckConnectivity` + `EnsureMinDegree`, предупреждение в консоли и в отчёте |
| В EKF при вырожденном/малосвязном графе матрица `S` плохо обусловлена или сингулярна | уже есть обработка ошибки `Sinv.Inverse` — оставить, но залогировать номер тика и degree графа на момент сбоя |
| Снижение точности локализации из-за меньшего числа измерений | это ожидаемый и измеряемый эффект — не баг, а предмет исследования; фиксируется в отчёте через сравнение RMSE по разным k |
| Пересборка kNN-графа на каждом тике — `O(n² log n)` | приемлемо для размеров сети в проекте (n ~ 8-50); при необходимости — пометить как TODO для kd-дерева |

## 3. Часть B — временная динамика координат и рост неопределённости

### 3.1 Модель

Разделяем два независимых источника ошибки, которые сейчас в проекте не различаются:

- **Истинное движение** (`TrueCoord`) — объект физически перемещается в пространстве. Модель: случайное блуждание с шагом `MotionSigma` за тик (расширяемо до модели с постоянной скоростью).
- **Деградация знания узла о себе** (`BelievedCoord`, `Uncertainty`) — узел не переизмеряет GPS каждый тик (или измеряет всё хуже — типичный сценарий dead reckoning/IMU без коррекции): σ его собственной оценки растёт по заданному математическому закону, а сама оценка "уплывает" случайным блужданием с этим σ.

Законы роста неопределённости `σ(t)`, где `t = tick·dt`:

| Закон | Формула | Смысл |
|---|---|---|
| `linear` | `σ(t) = σ₀ + k·t` | постоянный систематический снос (bias drift) |
| `sqrt` | `σ(t) = σ₀·√(1 + t/τ)` | классическое случайное блуждание (IMU-дрейф) |
| `exp` | `σ(t) = σ₀·e^(t/τ)` | быстро расходящаяся деградация (потеря сигнала коррекции) |

### 3.2 Изменения структуры `Node` (`utils.go`)

```go
type Node struct {
    ID            int
    InitialCoord  Point   // текущий "зашумлённый якорь" для регуляризации GD (обновляется каждый тик из BelievedCoord)
    CurrentCoord  Point   // результат GD+EKF — то, что видит "потребитель" системы
    TrueCoord     Point   // истинное положение (заменяет старый realCoords []Point)
    BelievedCoord Point   // то, что узел "думает" о себе — дрейфует и теряет точность со временем
    Uncertainty   float64 // текущее σ ошибки BelievedCoord относительно TrueCoord
    IsAnchor      bool
}
```

`realCoords []Point`, ранее живший отдельным слайсом в `main.go`, удаляется — все места, где он использовался (`printGradientMetrics`, `AnalyzeEKFHistory` и т.д.), переходят на чтение `node.TrueCoord`.

### 3.3 Новые функции в `utils.go`

```go
// MotionParams описывает параметры временной симуляции сети.
type MotionParams struct {
    Dt              float64 // длительность одного тика
    MotionSigma     float64 // σ случайного блуждания истинного положения за тик
    GrowthLaw       string  // "linear" | "sqrt" | "exp"
    GrowthRate      float64 // коэффициент k / 1/τ в законе роста σ
    BaseUncertainty float64 // σ₀ — начальная неопределённость BelievedCoord
}

// StepTrueMotion сдвигает TrueCoord всех НЕ-анкерных узлов на один тик
// (анкеры считаются неподвижными точками привязки по определению).
func StepTrueMotion(nodes []*Node, mp MotionParams, rng *rand.Rand)

// GrowUncertainty обновляет node.Uncertainty по выбранному математическому
// закону на момент t = tick·mp.Dt и "размывает" BelievedCoord на один шаг
// случайного блуждания с этим σ — так BelievedCoord всё дальше уходит от TrueCoord.
func GrowUncertainty(nodes []*Node, mp MotionParams, tick int, rng *rand.Rand)

// RefreshInitialCoord переносит BelievedCoord в InitialCoord перед очередным
// тактом оптимизации — это новый "зашумлённый якорь" для регуляризации GD.
// CurrentCoord НЕ сбрасывается — так реализуется warm start между тиками.
func RefreshInitialCoord(nodes []*Node)

// RecomputeDistances пересчитывает матрицу измеренных расстояний по текущим
// TrueCoord + шум dErr. Вынесено из main.go, т.к. теперь вызывается каждый тик.
func RecomputeDistances(nodes []*Node, distErr float64, rng *rand.Rand) [][]float64
```

### 3.4 Изменения в `ekf.go`

Текущий predict-шаг (`P.Add(P, Q)`) уже концептуально корректен для трекинга подвижной цели: рост `P` перед каждой коррекцией моделирует "мы всё менее уверены, т.к. объект мог сдвинуться со времени последнего замера" — это не требует переписывания. Единственное целевое изменение:

- **`q` в конфиге теряет смысл константы** — при активной временной модели рекомендуется завязать `Q` на `MotionParams.MotionSigma` (например `q_tick ≈ MotionSigma² `), чтобы шум процесса EKF был согласован с реальной интенсивностью движения, а не подбирался вручную независимо. Реализуется как опциональный режим: если `motion.enabled = true` и `q` в конфиге не задан (0), `RunEKF` берёт `q` из переданного параметра, рассчитанного в `main.go` на основе `MotionParams`.

### 3.5 Изменения в `main.go` — реструктуризация в тик-цикл

```go
// [Инициализация: как сейчас, но TrueCoord вместо realCoords, один раз]
...
graph := BuildKNNGraph(distances, k, neighborMode)
edges := EdgesFromGraph(graph)

var tickMetrics [][]float64
for tick := 0; tick < motionParams.Ticks; tick++ {
    StepTrueMotion(nodes, motionParams, rng)
    GrowUncertainty(nodes, motionParams, tick, rng)
    RefreshInitialCoord(nodes)

    distances = RecomputeDistances(nodes, dErr, rng)
    graph = EnsureMinDegree(BuildKNNGraph(distances, k, neighborMode), distances)
    edges = EdgesFromGraph(graph)

    RunGradientDescent(nodes, distances, graph, gAlpha, gLambda, gEps, gdItersPerTick)
    RunEKF(nodes, distances, edges, ekfItersPerTick, ekfQ, ekfR)

    tickMetrics = append(tickMetrics, CollectTickMetrics(tick, nodes))
}
SaveTickMetricsToCSV("tick_history.csv", tickMetrics)
AnalyzeTickHistory("tick_history.csv")
```

При `motion.enabled = false` (или `ticks = 1`) цикл вырождается ровно в текущее поведение — ещё один regression-чекпойнт.

### 3.6 Метрика компенсации — как измерить "насколько хорошо ГД+EKF справляются"

Новые функции в `utils.go`:

```go
// CollectTickMetrics считает на один тик:
//  - rawRMSE  — RMSE(BelievedCoord, TrueCoord): "сырая" ошибка без компенсации
//  - finalRMSE — RMSE(CurrentCoord, TrueCoord): ошибка после GD+EKF
//  - compensationRatio = rawRMSE / finalRMSE  (>1 — фильтр помогает, →1 — перестаёт справляться)
func CollectTickMetrics(tick int, nodes []*Node) []float64

// SaveTickMetricsToCSV пишет [tick, rawRMSE, finalRMSE, compensationRatio, edgeCount] по тикам.
func SaveTickMetricsToCSV(filename string, rows [][]float64) error

// AnalyzeTickHistory читает tick_history.csv и определяет:
//  - стабилизируется ли compensationRatio (система успевает за ростом ошибки)
//  - или монотонно падает к 1 и ниже (эффективность компенсации размывается быстрее,
//    чем алгоритм успевает считать) — и, если да, на каком тике происходит перелом.
func AnalyzeTickHistory(filename string) error
```

Это прямой ответ на условие задачи: "проверить, как хорошо связка ГД+EKF компенсирует нарастание ошибки" — через явный числовой `compensationRatio(t)` и тренд-анализ, а не только "красиво/некрасиво выглядит график".

### 3.7 Риски

| Риск | Митигация |
|---|---|
| При малом числе итераций GD/тик система не успевает сойтись до следующего сдвига | параметры `gd_iters_per_tick`/`ekf_iters_per_tick` конфигурируемы отдельно от "разовых" `max_iter`; фиксировать в отчёте зависимость качества от этого баланса |
| Несогласованный `q` (константа) при реальном движении даёт либо перегретый, либо "закостеневший" фильтр | опциональная привязка `q` к `MotionSigma` (см. 3.4) |
| Анкеры считаются идеальными и неподвижными всегда | зафиксировать как явное допущение текущей итерации; ослабление (медленный дрейф анкеров) — по желанию, вне рамок этого плана |
| Рост объёма CSV-логов (история на каждый тик × каждую итерацию) | по умолчанию писать в `tick_history.csv` только агрегаты по тику, а не полную GD/EKF-историю каждого тика (детальные `mod1_history.csv`/`ekf_history.csv` — только для последнего тика, для отладки) |

## 5. Порядок реализации (инкрементальные, тестируемые фазы)

**Фаза A — рефакторинг без изменения поведения**
Вынести `realCoords []Point` в `Node.TrueCoord`; вынести генерацию `distances` в `RecomputeDistances`. Проверка: вывод программы на всех текущих конфигах бит-в-бит идентичен (детерминировано зафиксировав seed rng на время теста).

**Фаза B — k-NN граф (топология)**
Добавить `NeighborGraph`/`Edge`/`BuildKNNGraph`/`EdgesFromGraph`/`CheckConnectivity`/`EnsureMinDegree`; прокинуть `graph`/`edges` в `RunGradientDescent`/`RunEKF`; CLI/TOML `k`, `neighbor_mode`.
Регрессионный тест: `k = n-1` даёт тот же результат, что и до изменений. Затем — прогон с уменьшающимся `k` и снятие деградации RMSE.

**Фаза C — временная динамика (без учёта k-NN, граф полносвязный)**
`MotionParams`, `StepTrueMotion`, `GrowUncertainty`, `RefreshInitialCoord`; тик-цикл в `main.go`; `CollectTickMetrics`/`SaveTickMetricsToCSV`/`AnalyzeTickHistory`.
Регрессионный тест: `ticks = 1` (или `motion.enabled = false`) даёт прежнее поведение.

**Фаза D — интеграция**
Совместный прогон k-NN + динамики: граф пересобирается каждый тик по актуальным (сдвинувшимся) координатам. Прогон новых конфигов `config/dynamic/*`, подбор `gd_iters_per_tick`/`ekf_iters_per_tick`/`q`.

**Фаза E — инструментарий**
`testbench.py`: новая функция построения графика `rawRMSE(t)` vs `finalRMSE(t)` vs `compensationRatio(t)` по `tick_history.csv`; обновление `report.md`/`report_images` под новые сценарии.

**Фаза F — валидация и выводы**
Серия прогонов по сетке `(k, growth_law, growth_rate)`, фиксация: при каких параметрах `compensationRatio` стабилизируется выше 1 (система справляется), а при каких — сваливается к 1 и ниже (не справляется). Результат — основа для раздела отчёта.

## 7. Открытые вопросы (на усмотрение автора проекта перед стартом реализации)

1. `mode="mutual"` vs `"union"` по умолчанию для k-NN — реализовать оба режима, но зафиксировать один как дефолт в конфигах.
2. Нужна ли модель движения анкеров (медленный дрейф опорных станций) или они остаются идеально неподвижными во всех сценариях — план выше фиксирует второй вариант как явное допущение.
3. Единица времени тика (`dt`) — привязывается ли к физическому смыслу (секунды) или остаётся безразмерным индексом итерации симуляции.
