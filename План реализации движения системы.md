# План реализации: асимметричная k-NN топология + временная динамика сети

## 0. Контекст и статус

Часть **временной динамики** (§3 старого плана) уже реализована и находится в `pkg/environ/kinematics.go`, `pkg/environ/env.go`, `cmd/main.go`: `Node.RealCoord/BelievedCoord/Uncertainty/TickCounter`, `StepTrueMotion`, `GrowUncertainty`, `RefreshInitialCoord`, `RecomputeDistances`, тик-цикл в `main.go`. Это не переделывается.

Не реализована **топология обмена данными** — `RunGradientDescent`/`RunEKF` сейчас всё ещё работают по полносвязной симметричной матрице `distances[n][n]` (двойной цикл `for i; for j:=i+1`). Файл `pkg/algorithms/k-nearest.go` создан, но пуст.

Этот план описывает переход от полносвязного симметричного графа к **асимметричному графу направленных измерений**, взамен изначально предполагавшейся симметричной k-NN топологии (mutual/union, `Edge{I,J}` с `I<J`).

### 0.1 Почему асимметрия, а не симметричный k-NN

Если узел A измеряет расстояние до узла B, а вокруг B есть скопление k других узлов ближе, чем A, — B не выберет A в свои k ближайших. Но A всё равно физически получил измерение до B и может его использовать. Модель "ребро A-B существует только если оба считают друг друга соседями" (mutual) или "хотя бы один" (union) обе размывают эту направленность через симметризацию постфактум.

Правильная модель: у каждого узла — свой независимый список из k ближайших целей по его собственным измерениям. Направление `A→B` и `B→A` — два разных, независимо существующих измерения. Понятие "ребро" (неориентированная пара) удаляется; вместо него — направленное измерение.

## 1. Изменение структур данных (`pkg/types/types.go`)

```go
// Measurement — направленное измерение расстояния: From измерил расстояние до To.
// From и To — индексы в nodes. Существование Measurement{A,B} не подразумевает
// существование Measurement{B,A}.
type Measurement struct {
    From, To int
    Value    float64 // измеренное расстояние (с шумом)
}
```

`NeighborGraph`, `Edge`, режимы `mutual`/`union` — не вводятся вообще (в исходном плане их предполагалось удалить после введения; в асимметричной модели они просто никогда не появляются).

`Config` — секция `[topology]` без `neighbor_mode`:

```go
Topology struct {
    K int `toml:"k"` // число ближайших целей на узел; k >= n-1 вырождает граф в полносвязный
} `toml:"topology"`
```

## 2. Построение топологии (`pkg/algorithms/k-nearest.go`)

```go
// BuildMeasurements строит асимметричный список направленных измерений:
// для каждого узла i берутся k ближайших (по measured distances[i][*]) целей j,
// независимо от того, что решит узел j про узел i.
// Анкеры измерения не инициируют (BuildMeasurements пропускает From=анкер),
// т.к. в текущей модели анкер не решает локализационную задачу — только служит
// целью для измерений подвижных узлов. Анкер как To — разрешён.
func BuildMeasurements(nodes []*types.Node, distances [][]float64, k int) []types.Measurement
```

Реализация: для каждого подвижного `i` — сортировка индексов `j != i` по `distances[i][j]`, взять первые `k`, для каждого добавить `Measurement{From: i, To: j, Value: distances[i][j]}`.

`CheckConnectivity` — сохраняется, но работает по направленному графу (BFS по исходящим `From→To`, обход в направлении, обратном измерению, поскольку именно узел `From` использует измерение до `To` для самокоррекции): для каждого подвижного узла проверяется, есть ли путь до анкера в графе, где ребро `From→To` трактуется как "From может опираться на To".

`EnsureMinDegree` — сохраняется в упрощённом виде: если у подвижного узла `i` ноль исходящих измерений (может произойти только при `k=0`, что является ошибкой конфигурации, а не следствием асимметрии) — не требуется, т.к. `BuildMeasurements` при `k>=1` всегда даёт каждому подвижному узлу ровно `min(k, n-1)` измерений. Функция удаляется из плана как избыточная.

`EdgesFromGraph`, `mode`-параметр — удаляются, как и планировалось изначально, но по другой причине: не после дедупликации, а потому что дедупликация направленных измерений в принципе не нужна — `Measurement{A,B}` и `Measurement{B,A}` сосуществуют как два разных элемента списка.

## 3. Градиентный спуск (`pkg/algorithms/gradient.go`)

```go
func RunGradientDescent(nodes []*types.Node, measurements []types.Measurement, alpha, lambda, epsilon float64, maxIter int)
```

Внутренний двойной цикл `for i { for j != i { ... } }` заменяется на плоский проход:

```go
gradients := make([]types.Point, n)
for _, m := range measurements {
    i, j := m.From, m.To
    if nodes[i].IsAnchor {
        continue
    }
    dCalc := types.Distance(nodes[i].CurrentCoord, nodes[j].CurrentCoord)
    errRatio := 1.0 - (m.Value / dCalc)
    gradients[i].X += errRatio * (nodes[i].CurrentCoord.X - nodes[j].CurrentCoord.X)
    gradients[i].Y += errRatio * (nodes[i].CurrentCoord.Y - nodes[j].CurrentCoord.Y)
    gradients[i].Z += errRatio * (nodes[i].CurrentCoord.Z - nodes[j].CurrentCoord.Z)
}
```

Важное следствие асимметрии: если `j` — тоже подвижный узел и у него нет обратного измерения до `i` (`i` не входит в его k ближайших), то `j` не получает встречного градиента от этой пары на данном тике. Раньше (симметричная матрица) каждая пара давала вклад в обе стороны одновременно. Это ожидаемое поведение новой модели, а не баг — но следствие: **скопление узлов вокруг B будет тянуться к B сильнее, чем B к ним**, что и является целью асимметрии. Зафиксировать это явно в отчёте (см. §6).

Регуляризация к `InitialCoord` (`lambda`-штраф) не завязана на измерения — остаётся без изменений, применяется один раз на узел после основного прохода.

## 4. EKF (`pkg/algorithms/ekf.go`)

```go
func RunEKF(nodes []*types.Node, measurements []types.Measurement, iterations int, q, r float64)
```

- `numMeas := len(measurements)` вместо `C(n,2)`.
- Цикл построения `H`/`Z`/`Zcalc` — один проход `for measIdx, m := range measurements { i, j := m.From, m.To ... }` вместо вложенного `for i { for j:=i+1 }`.
- Якобиан не меняется математически: `∂d/∂x_from = -∂d/∂x_to` остаётся верным для направленного измерения так же, как для симметричного — знак завязан на геометрию (`dx = x_from - x_to`), а не на порядок обхода пар. Заполнение колонок `H` для `si`/`sj` — как раньше, просто `i=From`, `j=To` жёстко фиксированы направлением измерения, а не порядком `i<j`.
- Если `Measurement{A,B}` и `Measurement{B,A}` оба присутствуют на тике — это **две отдельные строки** в `Z`/`H`, а не одна, как отмечено в постановке задачи. Обе учитываются независимо, `R` для них может быть одинаковым (общий шум дальномера).
- Анкер как `From` не встречается (см. `BuildMeasurements`), поэтому строка `H`, где `From` — анкер, невозможна; строка, где `To` — анкер, обрабатывается как раньше (нулевой вклад в колонки состояния анкера, т.к. его в `nodeToState` нет).

## 5. Главный цикл (`cmd/main.go`)

Замена вызовов:

```go
measurements := algorithms.BuildMeasurements(nodes, distances, k)
algorithms.RunGradientDescent(nodes, measurements, gAlpha, gLambda, gEps, gMaxIter)
algorithms.RunEKF(nodes, measurements, eIter, ekfQ, ekfR)
```

Внутри тик-цикла — та же замена, `measurements` пересчитывается каждый тик после `RecomputeDistances` (топология может измениться, т.к. узлы сдвинулись).

Новый CLI-флаг `-k` (по умолчанию `n-1`, что даёт вырождение в полносвязный граф — совпадает с текущим поведением, см. регрессионный чекпойнт в §7).

## 6. Риски асимметричной модели

| Риск | Митигация |
|---|---|
| Узел с малым числом входящих измерений (никто не выбрал его в top-k) слабо ограничен в GD/EKF извне — держится почти только на собственной регуляризации к `InitialCoord` | ожидаемый эффект скопления (см. §3); фиксируется в отчёте как сравнение "исходящая степень" vs "входящая степень" по узлам |
| `CheckConnectivity` должна анализировать направленный, а не неориентированный граф — путь `i → анкер` может не существовать, даже если неориентированная версия того же графа была бы связной | реализовать BFS по исходящим рёбрам `From→To`, не симметризовать |
| При `k` близком к `n-1` асимметрия почти исчезает (каждый узел видит почти всех) — эффект заметен только при малых `k` | фиксировать в отчёте диапазон `k`, при котором асимметрия даёт значимое расхождение с симметричной версией |
| EKF: `numMeas` может быть примерно вдвое больше, чем в старой симметричной модели при том же `k` (т.к. взаимные измерения не дедуплицируются) | учитывать при выборе `r`/`q`; отметить рост `numMeas` в логах на тик |

## 7. Порядок реализации

**Фаза A (уже сделана)** — временная динамика на полносвязном графе. Не трогать.

**Фаза B — асимметричная топология**
1. `types.Measurement` в `pkg/types/types.go`.
2. `BuildMeasurements`, `CheckConnectivity` (направленная версия) в `pkg/algorithms/k-nearest.go`.
3. Сигнатуры `RunGradientDescent`/`RunEKF` → принимают `[]types.Measurement`.
4. `cmd/main.go`: построение `measurements` вместо прямой передачи `distances`, включая внутри тик-цикла.
5. Регрессионный чекпойнт: при `k = n-1` результат (RMSE, сходимость) должен совпадать с текущим поведением на полносвязном графе — т.к. при `k=n-1` каждый узел измеряет вообще всех, и множество `Measurement` покрывает все упорядоченные пары `(i,j), i≠j`, что математически эквивалентно текущему двойному циклу по всем парам (с той разницей, что раньше каждая неупорядоченная пара учитывалась в GD один раз в сумме по `i`, а теперь — как и раньше, поскольку внешний цикл по `i` в GD и сейчас идёт по всем `i`). Для EKF при `k=n-1` `numMeas` вырастет с `C(n,2)` до `n(n-1)` (упорядоченные пары вместо неупорядоченных) — это ожидаемое расхождение, не баг; регрессия проверяется не побитово, а по итоговому RMSE/сходимости.

**Фаза C — конфигурация**
`[topology] k` в TOML-пресетах, CLI-флаг `-k`. Новые пресеты `config/topology/*.toml` с разными `k` для сравнения качества локализации.

**Фаза D — валидация**
Прогон по сетке `k` (включая малые значения, где асимметрия выражена сильнее всего), сравнение RMSE и `compensationRatio` (уже собирается тик-циклом) в разрезе "средняя входящая степень узла". Основа для раздела отчёта про эффект скоплений.

## 9. Открытые вопросы

1. Может ли анкер быть `From` (т.е. измерять расстояние до других и участвовать в top-k отборе)? Текущее допущение — нет, анкер только `To`, т.к. он не решает локализационную задачу и его "мнение" о соседях не нужно ни GD, ни EKF. Если у анкеров есть физический дальномер и его измерения могли бы дать дополнительную информацию — расширение вне рамок этого плана.
2. `CheckConnectivity`: используется ли для diagnostics-варнинга в консоли (как в исходном плане) или как жёсткая проверка, останавливающая прогон? План фиксирует первое (варнинг), т.к. GD/EKF и без связности деградируют предсказуемо (регуляризация к `InitialCoord` держит узел на месте), а не падают.
3. Единица времени тика (`dt`) и модель движения анкеров — вне рамок этого плана, не относится к теме топологии.
