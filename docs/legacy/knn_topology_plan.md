# Заметка: переход к асимметричной k-NN топологии измерений

> Историческая заметка (план, полностью реализован). Описывает переход от полносвязной симметричной матрицы измерений к направленному асимметричному списку измерений на основе k ближайших соседей. Итоговое описание топологии — см. [../02_concept.md](../02_concept.md), код — `pkg/algorithms/k-nearest.go`.

## Почему асимметрия, а не симметричный k-NN

Если узел A измеряет расстояние до узла B, но вокруг B есть скопление других узлов ближе, чем A, то B может не выбрать A в свои k ближайших соседей. При этом A всё равно физически получил измерение до B и может его использовать. Модель «ребро A–B существует только если оба считают друг друга соседями» (mutual) или «хотя бы один» (union) обе искусственно размывают направленность через симметризацию постфактум.

Выбранная модель точнее отражает физику измерений: у каждого узла — свой независимый список из k ближайших целей по его собственным измерениям. Направления `A→B` и `B→A` — два разных, независимо существующих измерения; понятие неориентированного «ребра» не вводится вовсе, вместо него — направленное `Measurement{From, To, Value}`.

## Изменения по компонентам

- **`pkg/types/types.go`**: структура `Measurement{From, To int; Value float64}` — существование `Measurement{A, B}` не подразумевает существование `Measurement{B, A}`. Секция `Config.Topology{K int}` без режимов `mutual`/`union` — они не вводились вообще.
- **`pkg/algorithms/k-nearest.go`**: `BuildMeasurements` — для каждого подвижного узла `i` сортирует остальные узлы по измеренному расстоянию `distances[i][*]` и берёт первые `k` в качестве целей. Анкеры не инициируют измерений (не могут быть `From`), но могут быть целью (`To`). `CheckConnectivity` — обход в ширину по направленному графу исходящих измерений `From → To`, а не по симметризованному графу.
- **`pkg/algorithms/gradient.go`**: внутренний двойной цикл по всем парам узлов заменён на плоский проход по списку измерений; при этом каждое измерение всё равно даёт градиент обоим концам пары (симметризация на уровне вклада в оптимизацию, а не на уровне списка измерений).
- **`pkg/algorithms/ekf.go`**: якобиан математически не меняется — `∂d/∂x_from = −∂d/∂x_to` верно для направленного измерения так же, как и для симметричного, поскольку знак определяется геометрией (`dx = x_from − x_to`), а не порядком обхода пар. Если `Measurement{A,B}` и `Measurement{B,A}` присутствуют одновременно — это две независимые строки в векторе измерений, а не дублирование одной.

## Известные следствия асимметрии (не баги)

| Эффект | Пояснение |
|---|---|
| Узел с малым числом входящих измерений слабо ограничен извне | Держится в основном на собственной регуляризации к `InitialCoord` — ожидаемый эффект, не требующий отдельной компенсации |
| Скопления узлов притягиваются к «центру» скопления сильнее, чем «центр» к ним | Прямое следствие направленности — целевой эффект модели, а не искажение |
| При `k`, близком к `n−1`, асимметрия почти исчезает | Каждый узел видит почти всех остальных, эффект значим только при малых `k` |
| Число измерений в EKF может быть почти вдвое больше, чем в старой симметричной модели при том же `k` | Взаимные измерения не дедуплицируются; учитывается при выборе `r`/`q` |

## Регрессионная проверка

При `k = n − 1` (полносвязный граф) результат должен совпадать по RMSE и сходимости с прежним поведением на явной полносвязной матрице — множество направленных измерений в этом случае покрывает все упорядоченные пары `(i, j), i ≠ j`, что даёт эквивалентный (хотя количественно не побитово идентичный из-за удвоения числа измерений в EKF) результат локализации.
